## 疑问澄清

### 需要确认的问题

1. **Mock 策略**：

   - 对于浏览器自动化模块（browser/），是否需要 Mock 浏览器驱动？
   - 对于二进制工具模块（binary/），是否需要 Mock 外部命令调用？

2. **集成测试**：

   - 是否需要保留现有的集成测试？
   - 集成测试是否需要修复？

3. **测试数据**：

   - 是否需要创建测试数据文件（如测试用的 Excel、CSV 文件）？
   - 是否需要 Mock 钉钉 API 响应？

4. **测试优先级**：

   - 是否优先测试核心业务模块（core/）？
   - 是否优先测试低覆盖率模块？

5. **测试环境**：
   - 是否需要配置测试环境变量？
   - 是否需要使用测试数据库？

### 智能决策

基于现有项目内容和行业最佳实践，我做出以下决策：

1. **Mock 策略**：

   - ✅ 浏览器自动化模块：Mock 浏览器驱动，避免实际启动浏览器
   - ✅ 二进制工具模块：Mock 外部命令调用，避免实际执行 FFmpeg 和 N_m3u8DL-RE
   - ✅ 文件操作：使用临时文件进行测试

2. **集成测试**：

   - ✅ 保留现有的集成测试
   - ✅ 修复集成测试中的错误
   - ✅ 集成测试使用 Mock 避免实际下载

3. **测试数据**：

   - ✅ 使用 pytest fixture 创建临时测试数据
   - ✅ Mock 钉钉 API 响应
   - ✅ 不创建持久化的测试数据文件

4. **测试优先级**：

   - ✅ 优先修复现有失败的测试
   - ✅ 优先测试核心业务模块（core/）
   - ✅ 优先测试低覆盖率模块（<50%）

5. **测试环境**：
   - ✅ 使用环境变量配置测试环境
   - ✅ 不需要测试数据库

## 风险评估

### 技术风险

1. **Mock 复杂性**：

   - 风险：浏览器自动化和二进制工具的 Mock 可能比较复杂
   - 缓解：使用 pytest-mock 的 patch 装饰器，仔细设计 Mock 对象

2. **测试稳定性**：

   - 风险：某些测试可能因为环境问题而不稳定
   - 缓解：使用 Mock 避免外部依赖，使用临时文件避免文件冲突

3. **覆盖率目标**：
   - 风险：某些模块可能难以达到 80%覆盖率
   - 缓解：优先测试核心逻辑，对于难以测试的代码添加注释说明

### 时间风险

1. **测试编写时间**：

   - 风险：编写完整的测试用例可能需要较长时间
   - 缓解：优先测试核心模块，逐步提高覆盖率

2. **测试修复时间**：
   - 风险：修复现有失败的测试可能需要较长时间
   - 缓解：先修复简单的测试，再修复复杂的测试
